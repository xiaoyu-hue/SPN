## 二、技术栈阵营（重要：按栈分群，避免混用）

**给 AI 的提醒：接到任务先问"这个项目属于哪个阵营"，别默认某一种。**

### 阵营 A：零依赖原生 JS
- **特点**：零构建、零运行时依赖，浏览器直接开 index.html
- **⚠️ 冲突**：不能引入 React 组件库、不能用 Tailwind（需要构建）、不能加 npm 依赖
- **改法**：手写 CSS + 原生 DOM 操作

### 阵营 B：React + Vite + TypeScript
- **特点**：有构建、有 npm 依赖、有测试
- **可引入**：React 生态组件库可用，但要控制依赖数量

### 阵营 C：Astro + Tailwind
- **特点**：静态生成、零运行时依赖是它的卖点
- **⚠️ 冲突**：加客户端 JS 会破坏"零运行时"这个定位

### 阵营 D：TypeScript + esbuild → IIFE
- **特点**：编译进 IIFE，但运行时仍是原生 JS
- **⚠️ 冲突**：不是 React 项目，别按 React 改

### 阵营 E：Node + Express（唯一有真后端的项目）
- **特点**：有服务端
- **⚠️ 已知问题**：单密码鉴权、无 CSRF 防护、默认密码写在 README 里（部署前必须改）

## 四、我的三条真实判断（给 AI 理解我的决策风格）

1. **第一次上线**：AI 推荐了几个静态平台 → 我自己选定，额度用完后自己配了备用站
   → **AI 列选项，我选**
2. **两种视觉风格能不能融合**：AI 说没法保证 → 我直接试，成了整站视觉基调
   → **可逆的事，先试**
3. **某加密项目的安全边界**：AI 写出了加密代码 → 我自己写进 README"未经审计""不建议用于敏感场景"
   → **能跑不等于我能担保**

## 五、文档里的数字不写死

我的 README 里原来写着具体数字（"573 测试""v6.5.1""192 时间线"等）。
现在我改了做法——**这些数字不写死，改用相对描述。**

### 为什么改
数字一改代码就失真。而"如实写局限"是我所有项目的立身之本，
**失真的数字会把这条原则变成反例**——比不写更伤信任。

### 但不能改成模糊说法
"有大量测试"没有信息量，读者只会觉得我在含糊。
**诚实需要具体，具体才有代价。**

### 我的新写法（相对描述）

| 原来写死 | 现在改成 |
|---|---|
| 11 模块 · 573 测试 · v6.5.1 | 十余个模块 · 数百项测试 · 迭代到第六个大版本 |
| 319 测试 · v1.8.1 | 三百余项测试 |
| 7 种板块 · 8 套主题 · 123 测试 | 多种板块与多套主题 · 百余项测试 |
| 192 时间线 · 40 工具 · 37 书 | 近两百条时间线 · 约四十个工具 |
| 158 测试 · v1.16.1 | 百余项测试 |

### 保留直接写的部分
结构性事实不变，照写：
"数据存浏览器本地""零运行时依赖""无支付闭环""端到端加密"——
**这是定位，不是数量，不会失真。**

### 给 AI 的规则
写任何文档时，不要写死会随代码变化的数字。
用相对描述，或在必须给精确值时标注"截至某版本"。
改代码影响了文档里的数字，必须同步改，并在交付汇报里单独说明。
