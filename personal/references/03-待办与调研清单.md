## P0｜（示例）移动端适配：UI / 布局

**状态：未开始（待调研）**

### 你原话（示例占位）
> "我希望界面、UI、布局更适合手机移动端，有那种大厂质感，但我不会描述那种感觉。"

### 先纠正一个前提
**不是你不会描述，是这类感受本来就没有现成词汇。**
"大厂质感"拆开是几个**可测量**的东西：

| 你感觉到的 | 对应的具体东西 |
|---|---|
| 舒服 | 间距系统（4/8/12/16/24 这套栅格，不是随手写的 px） |
| 高级 | 克制的色彩（一个主色 + 中性灰阶，不是每个按钮一个颜色） |
| 跟手 | 触控目标 ≥44px、点击有即时反馈 |
| 稳 | 有加载态、空态、错误态，不是白屏或卡住 |
| 统一 | 圆角、图标风格、动效曲线全局一致 |
| 不拥挤 | 移动端单列优先、底部导航、信息密度按屏分层 |

**所以调研方向不是"找一个好看的模板"，是找设计规范 + 可复用的组件实践。**

### 调研清单（示例）
- [ ] 大厂设计规范原文（不是二手解读）
- [ ] GitHub 开源参考（组件库、可复制源码的设计系统、获奖级站点收录）
- [ ] 开源 skill / 工具：有没有专门做 UI 审查的

### 我的初步判断（等调研验证，先别当结论）
- 不同项目技术栈差异大，统一适配前应该**先分两类处理，不要一刀切**。
- ⚠️ 更要紧的冲突：零依赖原生 JS 项目的"零依赖、零构建"是写在 README 里的卖点，
  如果为了移动端引入组件库，**等于拆掉自己的定位**。

所以这里有个真实的取舍要你拍板：
- **路线一**：引入组件库重做 → 开发快、效果好，但零依赖卖点没了
- **路线二**：补齐设计规范但保持零依赖 → 保住定位，但工作量全在手写 CSS 上
