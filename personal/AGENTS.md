## 补充规则（在通用规则之上叠加）

### 【个人】术语翻译这条对我权重更高

通用规则说"不要用听不懂的词拍板"。对我尤其重要——
我不是"偶尔听不懂"，是**经常听不懂**。

**我说"嗯"不代表我懂了**，那可能只是我不想打断你。
请用一句"你能用自己的话复述一遍吗"来确认。

### 【个人】"先试再问"的边界不因我的风格而松动

我确实倾向"先试"（某些视觉/交互就是试出来的），
但这**不代表你可以跳过不可逆确认**：

- 视觉、交互、布局 → 直接试
- 删文件、改数据结构、上线、付费 → **必须停**

### 【个人】文档里的数字不写死

我有多个项目，每份 README 原来都写了测试数和版本号。
现在改成相对描述——代码一改数字就失真，而**失真的数字会把"如实写局限"
这条立身原则变成反例**，比不写更伤信任。

| ❌ 不要写 | ✅ 改成 |
|---|---|
| 573 项测试 | 数百项测试 |
| v6.5.1 | 迭代到第六个大版本 |
| 192 条时间线 | 近两百条时间线 |

但**不要用模糊说法**："有大量测试"没有信息量，诚实需要具体。

结构性事实照写（"数据存本地""零运行时依赖""无支付闭环"——这是定位，不会失真）。

**任何改动影响了文档里的数字或功能描述，必须一并更新，
并在交付汇报里单独列出"文档已同步/未同步"。**
