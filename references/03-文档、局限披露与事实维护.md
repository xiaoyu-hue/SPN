# 文档、局限披露与事实维护

> 核心原则：**与其说谦虚，不如说是把边界说清楚。**
> 规律是——先说清做不到什么，别人才会信你做得到什么。
> 推论——**写进去的每一个数字，都必须永远是准的。** 失真的数字比不写更糟。

---

## 零、先解决数字问题（最容易失真的部分）

### 为什么这是个真问题

你会想在 README 里写"573 项测试""v6.5.1""192 条时间线"——这些数字很有说服力。
但代码一改，测试可能变成 601 项，版本升到 v6.6.0，时间线加到 200 条。

**数字一失真，"如实写局限"就变成了"如实写……曾经如实过"。** 这比不写更伤信任。

### 但不要干脆不写数字

把"573 项测试"改成"有大量测试"是**倒退**——模糊的数字没有信息量，
读者只会觉得你在含糊其辞。诚实需要具体，具体才有代价。

### 正确做法：分三类处理

| 类型 | 例子 | 怎么办 |
|---|---|---|
| **结构性事实**（很少变） | "数据存浏览器本地""零运行时依赖""无支付闭环" | **直接写**。这是定位，不是数量 |
| **过程性数字**（每次改都可能变） | 测试数、版本号、条目数、模块数 | **不要手写死**。见下面三种写法 |
| **外部引用数据**（别人的调研） | CVE 编号、调查报告里的统计 | **保留但必须标核实日期**，并提醒复核 |

### 过程性数字的三种写法（从糙到好）

**写法一：相对描述（最省事，推荐先用这个）**

用"量级 + 趋势"代替精确数字，说服力基本保留，但不会失真：

| ❌ 写死 | ✅ 相对描述 |
|---|---|
| 573 项测试 | 测试积累到数百项 |
| v6.5.1 | 迭代到第六个大版本 |
| 11 个模块 | 模块数增长到两位数 |
| 192 条时间线 | 近两百条时间线 |
| 7 种板块 · 8 套主题 | 多种板块与多套主题 |

**关键**：相对描述仍然具体（"数百项"比"很多"具体），只是不承诺精确值。

**写法二：单一数据源（更严谨）**

数字只在**一个地方**定义，其他文档引用它，而不是各自手写一份。

```
PROJECT_FACTS.md        ← 唯一真源：版本、测试数、条目数
    ↓ 引用
README.md               ← 引用上面的文件，不重复写数字
```

改代码时只改 `PROJECT_FACTS.md` 一处。

**写法三：自动生成（最省心，但要会配 CI）**

- 版本号：从 `package.json` 或 git tag 自动读
- 测试数：CI 跑完测试后自动写回 README
- 条目数：用脚本从数据文件统计

**⚠️ 我的建议**：如果你已经有 CI 门禁，可以从"版本号自动读"开始试，
不要一上来全套自动化——配置本身也是维护成本。**先用写法一，够用很久。**

### 给 AI 的硬规则

```
文档中不要写死会随代码变化的数字（测试数、版本号、条目数、模块数）。
用相对描述代替："数百项测试"而不是"573 项测试"。
如果必须给精确值，标注日期或说明"截至某版本"。
改代码时如果影响了文档里的任何数字，必须同步更新，并在交付汇报里单独说明。
```

## 一、README 骨架

按这个顺序写，前四块决定别人要不要往下读：

```
1. 一句话定位（这个项目是什么、给谁用）
2. 🔗 在线地址（能直接试的链接，比任何描述都有说服力）
3. 🛠 技术栈 + 测试数量 + 许可证（一行搞定）
4. 快速开始（在线体验 / 本地运行）
5. 它想解决的那个具体问题
6. 已知局限        ← 不能省
7. 不适合什么场景  ← 不能省
8. 维护状态（含更新日期）
9. 联系与反馈（接受什么、不接受什么）
```

## 二、"做不到什么"怎么写（三种句式）

### 句式 A：直接列事实
> 无跨设备自动同步（需手动导入备份）、无团队协作、不是原生 App、浏览器数据可能被清理

### 句式 B：先说原因再说结论
> 虽然用的都是前沿技术（X25519 密钥协商、每消息 HKDF、Ed25519 签密文），但我是站在巨人的肩膀上实现自己的想法而已——我不是密码学专家。所有已知局限都如实写在了 README 里，没有藏起来。

### 句式 C：主动防止被误读
> 说句实话，免得被误读成权威推荐：时间线加进去主要是为了页面更好看；工具箱和读书推荐里的清单，大部分是我让 AI 帮我推荐的，我自己也没全读完。所以本意是自用，不是"我逐条读过、用过、判断过"的专家清单。

**句式 C 是最难也最有力量的一种：主动拆掉别人可能给你的、你不该要的信任。**

## 三、按项目类型的写法范例（可直接改）

### 本地优先型应用（数据存浏览器）
```
不适合 / 已知局限
- 无跨设备自动同步，换设备需手动导出导入备份
- 数据存在浏览器本地，清理浏览器数据会一并清掉
- 不是原生 App，无系统级通知
- 依赖较新版本的 Chrome / Edge / Safari
```

### 涉及加密 / 隐私的项目
```
⚠️ 关于 [项目名]
- 未经专业安全审计，不建议用于真实敏感场景
- 作者非专业开发者出身，代码由 AI 协助实现
- 安全问题欢迎讨论，但那不构成担保
- 请不要用它处理真正敏感的事
```

### 带后台的模板类项目
```
不适合 / 已知局限
- 单密码鉴权，无多管理员
- 无 CSRF 防护
- 单进程文件读写，不适合高并发
- 无 SSR / SEO
- 不适合支付类站点
⚠️ 后台默认管理密码写在 README 里，部署上线前务必先改掉
```

### 内容聚合类项目
```
- 内容由作者手工整理（非全量自动抓取）
- 清单多为 AI 推荐，并未逐条亲测
- 部分外链依赖第三方可用性
- 更新频率取决于作者时间
```

## 四、维护状态：怎么写"我慢下来了"

```
维护状态（2026-10 更新）：项目仍在维护，但节奏比之前慢——
主力设备坏了，现在用备用设备更新，等买了新机器会恢复。
它没有被放弃。如果你打算正式使用，请先读 README。
```

三个要素：**事实 + 原因 + 对用户的实际影响**。不要只说"最近比较忙"。

---

## 五、"不接什么"也要写清楚

```
🙅 不接的
付费定制开发、帮别人做安全审计、作业代做、"帮我改我的代码"
```

写了这条，能省掉未来 80% 的无效沟通。

## 六、许可证怎么选

常见做法：**代码与文档采用不同许可证。**

| 许可证 | 特点 | 什么时候选 |
|---|---|---|
| **MIT** | 最宽松，几乎无限制 | 想让最多人能用 |
| **Apache-2.0** | 宽松，但含专利条款，企业友好 | 企业场景、担心专利 |
| **AGPL-3.0** | 最强传染性，网络服务也必须开源 | 想堵住"拿去改改做成商业服务"的路（隐私类项目常用） |
| **CC BY** | 文档用，署名即可，可商用 | 文档想被广泛传播 |
| **CC BY-NC** | 文档用，禁商用 | 文档不想被拿去卖 |
| **CC BY-NC-SA** | 文档用，禁商用 + 相同方式共享 | 最严格的文档许可 |

**注意**：GitHub 自动识别的 SPDX 目前只支持 13 种许可，CC 系列只认 CC0-1.0。
所以用了 CC BY-NC 的仓库侧栏不显示许可徽章（API 返回 `NOASSERTION`）——这不是错误，
在 README 里说明"以 LICENSE 文件为准"即可。

## 七、让 AI 写 README 时的提示词

```
给这个项目写 README。要求：
1. 开头一句话说清它是什么、给谁用
2. 必须包含"已知局限"和"不适合什么场景"两节，如实写，不许粉饰
3. 如果某部分内容是 AI 推荐/生成的而非我亲测，明确标注出来
4. 在线地址和本地运行方式分开写
5. 维护状态写真实情况，含更新日期
6. 不要用"强大的""革命性的""极致体验"这类词
```
