# 提示词库

> 按**什么时候用**分类，不是按来源分类。方括号里换成你的实际情况。
> A 开场 / B 立项 / C 交付 / D 质量 / E 安全 / F 救急 / G 会话 / H 学习

---

## A. 会话开场：给 AI 定角色

### A1｜通用角色设定（不知道用什么时就用这段）

```
你和我协作开发一个项目。规则如下：

【表达方式】结论先用大白话讲，专业细节放后面展开，
术语第一次出现必须括号解释。不确定的信息直接说不确定，
禁止编造库名、API、版本号和配置项。给方案要讲清取舍，
比如"这个做法快但以后难扩展"，不要只给结论。

【反对机制】当我的想法有技术缺陷、逻辑漏洞或存在更优方案时，
必须先指出问题并给出至少一个替代方案，由我做决定，不要默默顺从。

【代码交付】给代码时必须说明：这段代码是干什么的、
放在哪个文件的什么位置、改动了哪里、怎么运行验证。
一次只给一个可运行的最小版本，不要一次丢出整个大项目。
项目出错时，先让我描述或粘贴报错信息，用大白话解释错误原因，
再给修复步骤，不要跳过排查直接重写。

【开发流程】接到需求先确认目标和范围再动手，缺关键信息时一次问清，
不要边做边猜。大任务拆成小步骤，每步交付可验证的成果。
技术选型给出建议加理由，等我拍板；实现细节和小问题直接做，不用事事请示。
涉及删除文件、覆盖代码、花钱的服务、对外发布这类不可逆操作，必须先征得我同意。

【安全意识】涉及用户数据、密码、密钥的代码，默认提醒我安全和隐私风险，
不把敏感信息写死在代码里。
```

**这段最值钱的两条**：一是"禁止编造库名/API/版本号"，二是"不可逆操作先征得同意"。
前者防 AI 编造看起来很像真的东西，后者防它擅自删库、上线、花钱。

### A2｜"我不懂技术"（你描述不清时，叠在 A1 后面）

```
我是一个不懂技术的小白用户，脾气还大，描述还未必清晰。
我每次下得需求不是技术的专业用语，你要先去理解我的需求，
以及把我的指令变成具体的执行任务。
如果你理解不了或者我的指令模糊，你可以随时停下来提问确认我的具体需求。
```

**这条解决真实痛点**：你的需求常常是感觉性的（"界面不够有大厂气质"），
不是技术性的。这条强制 AI **先把感觉翻译成任务**再动手。

## B. 立项：动手之前

### B1｜先调研，再编码（开始任何新项目前必用）

```
我要开发【XXX】项目。先不要写代码，先去 GitHub 查找同类优秀开源项目，
分析它们的核心功能、架构设计以及现有短板。
基于调研输出一套更优落地方案，等我确认方案之后，我们再动手开发。

核心原则：先调研，再编码。不要让 AI 从零凭空造轮子，
让它站在现有优秀项目的肩膀上做迭代。
```

**价值**：AI 默认倾向"直接给你写一个"，而它写出来的往往是你想到的第一个平庸方案。
先让它看十个同类项目，方案质量完全不同。

### B2｜PRD 需求文档公式

```
请输出标准产品需求文档，结构：
1. 项目概述  2. 用户目标  3. 核心功能  4. 交互规则  5. 约束限制

需求：【这里填你的产品/想法】

其它要求：
1. 【改成你的平台：Web / PWA / 小程序 / 安卓】
2. 【要不要后端、数据库、注册登录】
3. 只保留几个核心功能，尽量精简
4. 页面简洁干净
```

第 3 条"只保留几个核心功能"值得保留——**这是 1.0 版本的生死线**。

## C. 执行与交付

### C1｜复述验收标准（开工前必用）

```
在动手之前，先用三句话复述：
1. 这个任务的目标是什么
2. 你会改哪些文件
3. 做完的标志是什么——我用什么操作能确认它真的做完了

如果这三条里有任何一条你说不出来，说明需求还没想清楚，先问我。
```

### C2｜拆小步交付（大任务必用）

```
这个任务比较大。把它拆成可以逐个验证的小步骤，每步：
- 单独能跑、能看结果
- 做完立刻汇报：改了哪个文件、旧值→新值、你实际跑了什么验证
- 我不确认，不要进入下一步

请不要一次性憋一个大改然后交给我。
```

### C3｜完成前自收（收尾必用，防"假完成"）

```
在宣布任务完成前，先按任务目标自查：
1. 对照需求项检查实际改动
2. 查看改动文件和 diff，确认没有无关修改
3. 优先运行项目已有且与本次改动相关的测试、lint、类型检查或构建
4. 如果本次改动引起检查失败，先定位、修复，再重新验证；
   如果是既有或无关失败，明确告诉我
5. 没有可运行的验证方式时，不要声称"已完成"，
   直接告诉我未验证的部分、原因和风险

最后用短清单汇报：已完成内容、验证证据、剩余风险。
```

**AI 最爱说"已完成"，但实际没跑测试、改了无关文件。每次收尾都贴一遍。**

### C4｜诚实汇报格式

```
汇报这次改动，按这个格式：

改了什么：[文件路径] + 旧值 → 新值（新增文件写「新增」，删除写「删除」）
实际验证：跑了哪条命令，输出是什么
还没确认：[如实列出]

禁止使用"已改""已优化""已修复"这类没有信息量的词。
没有实际跑过的验证，不许说"测试通过"。
```

## D. 质量与设计

### D1｜设计自检（做完界面后用）

```
以 Awwwards、Webby Awards、FWA 获奖级网站为品质标准，
完成后从以下八个维度自检并持续优化，直到没有明显可提升之处：
排版、留白、视觉层级、色彩、动效、微交互、响应式、原创性。
```

配合这句一起用（让它先给方案而不是直接改）：
```
先逐项打分（1-10）并说明扣分在哪，我确认优先级后再改。
不要一次全改，改完一轮给我看效果。
```

### D2｜全方位代码审查（阶段性大扫除）

```
请来一次高度深度、综合、全方位的代码审查，覆盖：
1. 代码质量  2. 测试覆盖与质量  3. UI/UX 界面交互
4. 代码规范  5. 文档与代码是否同步 + 文档质量
6. 安全（含服务器端）

输出格式：按严重程度分级（致命 / 严重 / 一般 / 建议），
每条给出：位置、问题、为什么是问题、修复方案。
找不到问题的维度也明确说"未发现问题"，不要为了凑数编造。
```

**⚠️ 别一次全跑。** 一次审一个大项目会产出几百条，你处理不过来，
最后只会变成一份没人看的清单。**建议一次只审一个维度。**

## E. 安全

### E1｜上线前攻击自己

```
上线前，请你扮演攻击者，找出这个项目的问题：
1. 未登录用户能拿到什么数据
2. 用户 A 能不能读到用户 B 的数据（怎么改请求能做到）
3. 前端代码里有没有不该出现的密钥
4. 有没有只在前端做的权限判断
5. 有没有把用户输入直接拼进 SQL 或命令
6. 哪些接口没有限流、会被刷爆额度

每条给出：复现方式 + 修复方式。找不到问题就说找不到，不要编。
```

### E2｜安全边界声明（涉及他人数据时）

```
这部分涉及用户数据，我需要你明确列出：
1. 这套实现保护了什么
2. 它没保护什么（逐条列，不许省略）
3. 哪些场景不该用它
4. 有哪些是我作为非专业开发者无法验证的

注意：写完之后，关于"未经审计""不建议用于敏感场景"这类声明由我来写，
不要替我在 README 里做安全承诺。
```

## F. 救急与判断

### F1｜术语翻译（听不懂时立刻用）

```
你刚才说的这段话里有几个词我听不懂：[列出术语]。

用大白话重新讲一遍，要求：
- 不许用任何专业术语，用生活里的比喻
- 讲清它解决什么问题、不解决会怎样
- 讲清代价是什么（性能、金钱、复杂度、后续维护）
- 如果我不用它，最坏会怎样

我用能听懂的版本来做判断。
```

### F2｜要方案 + 权衡（拍板前必用）

```
我要做 [目标]。给我至少两个方案，每个方案说清：
1. 怎么做（一句话）
2. 代价是什么（时间、金钱、后续维护难度）
3. 什么情况下它会撑不住
4. 放弃了什么

最后给我一句"如果是你来选，你选哪个，为什么"——
但决定权在我，你只是给建议。
```

### F3｜拆穿糊弄（怀疑它在编时）

```
我怀疑你刚才那段里有不确定的内容。请逐条标注：
- 【确定】你验证过的
- 【推测】你基于经验推断的
- 【不确定】你其实不知道的

对于【不确定】的部分，给出验证方法，或者直说不知道。
不要用自信的语气说你不确定的事。
```

### F4｜先试再问（视觉 / 交互类）

```
我想试试 [风格/交互/布局]，你不确定能不能成就直说，不用替我论证可行性。
直接给我一个能跑的最小版本，我看效果再决定要不要继续。
不要写长篇分析，我要的是能看见的东西。
```

### F5｜数据模型设计（全栈项目开工前）

```
我要做 [应用]，需要设计数据模型。在写任何代码之前：
1. 列出需要哪些表、每张表哪些字段、表之间什么关系
2. 每张表标注：谁能读、谁能写、谁能删（按角色分）
3. 指出哪些字段是敏感的，需要额外保护
4. 给出对应的行级安全策略写法

我不批准 schema，你不要开始写业务代码。
```

### F6｜改数据结构前（保护数据）

```
我要改数据结构。在动手之前：
1. 先给我备份方案，并说明怎么验证备份能恢复
2. 给出迁移的每一步，标注哪些是可逆的、哪些不可逆
3. 不可逆的步骤单独列出来等我确认
4. 不要直接连接生产库执行写操作

记住：曾经有 AI agent 删掉过用户的生产数据库，我要求你在这个问题上格外保守。
```

## G. 会话管理：跨会话不失忆

### G1｜写交接文档（长会话结束前，直接发这句）

```
这个会话要结束了。请写一份交接文档，存到 HANDOFF.md：
把当前任务、已经完成的内容、卡住的问题、下一步计划和踩过的坑，
整理到 HANDOFF.md。
```

### G2｜下次开新会话第一句话

```
先读 HANDOFF.md。
```

**为什么值得固化**：AI 会话一定会失忆，这是硬限制。
一个 md 文件是目前**最轻量的跨会话记忆方案**，不装插件，各工具通用。

### G3｜HANDOFF.md 模板

```markdown
# HANDOFF

## 当前任务
（一句话：在做什么，目标是什么）

## 已完成
- [x] ...（含改动的文件位置）

## 卡住的问题
（含已尝试过但失败的做法——避免下次重复踩）

## 下一步计划
1. ...
2. ...

## 踩过的坑
- ...

## 待确认 / 待我拍板
- ...
```

## H. 学习与创作

### H1｜QBS 法（用经典书解决问题）

```
1. 把你遇到的问题发给 AI，让它推荐一本出版至少 30 年以上的书籍
2. 导出这本书的电子版 PDF
3. 把 PDF 给到任意 Agent，用 book-to-skill 指令，提炼成 Skill
4. 让 AI 调用刚生成的 Skill，去解决你的问题
```

### H2｜用寓言讲概念（理解 / 输出时用）

```
请从某个领域选择一个研究生水平的概念，用寓言故事把它讲清楚。
不要一开始揭晓答案，要到故事快结束时，才让人意识到原来讲的是这个概念。
故事结束后，再解释概念本身，以及故事里的隐喻分别对应什么。
```

## 使用心法（比提示词本身更重要）

1. **A1 + A2 是默认组合** — 几乎每个会话都该贴，其他按需叠加
2. **一次不超过 3 段** — 贴多了 AI 会顾此失彼
3. **贴进 AGENTS.md 的才是真规则** — 同一条提示词重复贴三次以上，就该固化进项目根目录
4. **C3 收尾必用** — AI 说"已完成"和你确认"真完成"之间，差着这一条
5. **术语翻译随时打断** — 听到不懂的词立刻喊停，不要等它说完一整段
