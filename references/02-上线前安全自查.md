# 上线前安全自查清单

> 适用：任何带后端、数据库、用户登录的项目。
> **这份清单存在的理由：权限错误在演示里完全看不出来。** 表锁着和敞着，页面长得一模一样——所以必须主动攻击自己。

## 为什么必须做

这不是理论风险，已经大规模发生过（以下均为公开报道，核实于 2026-10）：

- **CVE-2025-48757**：扫描 1645 个 AI 生成的应用，其中 170 个的 Supabase 数据表可被未认证读写，暴露邮箱、地址、第三方 API 密钥
- **UpGuard 调查**：在 Supabase 托管的数据库中发现约 1.6 万个存在不同程度个人数据暴露的项目，涉及姓名、地址、电话，以及少量密码和认证令牌
- **RedAccess（2026-05）**：扫描约 38 万个公开可访问的 AI 生成应用，约 5000 个在泄露敏感数据
- **Wiz 发现**：使用这类平台的组织中，约五分之一至少存在一类系统性漏洞

**根因都一样：AI 优化的是"演示能跑"，而安全边界是唯一不产生可见结果的部分。**

## 一、数据库权限（最高优先级，先做这个）

以下以 Supabase / Postgres 为例。其他后端请按对应机制调整。

### 检查 1：哪些表没开 RLS
在 SQL 编辑器里跑：
```sql
select tablename from pg_tables
where schemaname = 'public' and not rowsecurity;
```
返回任何一行 = 那张表此刻对全世界可读可写。

### 检查 2：已有策略是不是形同虚设
```sql
select tablename, policyname, qual
from pg_policies where schemaname = 'public';
```
重点看 `qual` 是 `(true)` 或完全没引用 `auth.uid()` 的——**那等于没锁**。
`auth.role() = 'authenticated'` 也不合格：它只验证了"登录了"，没验证"是不是你自己的数据"。

### 检查 3：像攻击者一样试一次
项目 URL 和 anon key 在浏览器里就能拿到（anon key 本来就是公开的，不是秘密）：
```bash
curl "https://YOUR-PROJECT.supabase.co/rest/v1/profiles?select=*" \
  -H "apikey: YOUR_ANON_KEY"
```
不登录就能拿回数据 = 正在泄露。空数组或权限错误才是对的。

### 正确写法
```sql
alter table public.documents enable row level security;

create policy "Users read own docs" on public.documents
  for select to authenticated
  using ( (select auth.uid()) = user_id );
```
`auth.uid()` 对匿名返回 null，所以匿名访问者拿不到任何行。用 `(select auth.uid())` 包一层让 Postgres 每查询算一次而不是每行算一次。

### 容易漏的四个点
1. **第一张表配了策略，后面加的几张没配** — 最常见的翻车方式
2. **anon 角色的 grant 没回收** — 加策略不撤销授权，anon 仍有写入路径
3. **`USING (true)`** — 看起来像权限，实际等于公开
4. **视图和 SECURITY DEFINER 函数** — 会绕过底层表的 RLS

## 二、密钥检查

前端构建产物里搜：
```bash
grep -r "service_role\|sk_live\|AKIA[0-9A-Z]\{16\}" dist/ build/ .next/ 2>/dev/null
```
**任何命中都是严重问题。** anon key 出现在前端是正常的（它本来就是公开的），service_role 出现则是致命的。

另外：
- `.env` 必须在 `.gitignore` 里，且**在第一次 commit 之前**就加进去
- 密钥进了 git 历史，删掉那一行也没用——历史里还能翻出来，必须**轮换**
- 推送到公开仓库前跑一次 `gitleaks detect`
- GitHub 公开仓库可免费开启 **Secret Scanning** 和 **Dependabot**

## 三、越权测试（必须自己动手做）

1. 注册**两个**账号 A 和 B
2. 用 A 创建一条数据
3. 用 B 去读它——改请求里的 id、改 URL 参数都行
4. **B 能读到 = 权限没配对，回去重做**
5. 完全退出登录后，直接访问需要登录的页面——能打开 = 服务端没校验

据公开审查数据，约 24% 的 AI 生成应用存在认证逻辑被反转的问题：未登录访客有完整权限，真实用户反而被挡在外面。

## 四、其他必查项

| 项 | 怎么做 |
|---|---|
| 服务端校验 | 所有输入在服务端校验，禁止拼接 SQL。AI 几乎不会主动加，要明说 |
| 限流 | 注册、登录、发邮件、AI 调用这类"花钱的接口"必须限流，否则一个脚本能烧掉额度 |
| CORS | 锁到自己的域名，不要留 `*` |
| 依赖漏洞 | 跑 `npm audit`。AI 生成的项目几乎从不做这件事 |
| 错误信息 | 不要把堆栈、SQL、内部路径返回给前端 |
| 备份 | 免费档通常不含自动备份——自己定导出计划并**验证过能恢复** |
| 日志 | 至少记录失败登录和错误，否则你只能等用户来告诉你出事了 |

## 五、免费安全扫描工具

| 工具 | 查什么 | 免费吗 |
|---|---|---|
| `npm audit` | 依赖漏洞 | 免费，Node 自带 |
| Gitleaks | git 历史里的密钥 | 免费，本地跑 |
| Semgrep | 代码逻辑漏洞（越权、注入） | 有免费档 |
| Snyk Code | 依赖 + 代码，能标出"真能触发"的漏洞 | 有免费档 |
| GitHub Secret Scanning | 推送到 GitHub 的密钥 | 公开仓库免费 |
| GitHub Dependabot | 依赖自动更新 + 告警 | 免费 |
| Supabase 自带 linter | RLS 未开启、策略过宽 | 免费（用 Supabase 才有） |

**⚠️ 重要限制**：这些是**静态检查**。它们抓不到"用户 A 能读到用户 B 数据"这类运行时逻辑问题——
那必须用 `04-提示词库.md` 的 E1 提示词手动攻击自己，或写动态测试。

## 六、最小实验：六步摸清全栈边界

不要一上来做完整应用。做"带登录的留言板"就够了：

1. 建表 + 开 RLS + 写策略
2. 邮箱登录
3. 登录后能发、能看自己的
4. 部署上线
5. **注册第二个账号，去读第一个账号的数据** ← 这步最关键
6. 读到了 = 权限没配对，重来

**第 5 步不是可选项。**

## 七、写给 AI 的硬规则（贴进 AGENTS.md）

1. 每张表必须开 RLS 并写策略，禁止 `USING (true)` 这种看着像权限、实际等于公开的写法
2. 密钥只在服务端，前端代码里出现 service_role / sk_live 立刻停下
3. 权限判断必须在服务端，前端藏按钮不算权限
4. 所有输入服务端校验，禁止拼接 SQL
5. 不可逆操作（删表、改结构、上线、付费）必须先问我
6. 改数据结构前先备份，不让 AI 直接连生产库执行写操作

第 6 条有真实先例：2025 年 7 月，Replit 的 agent 在一次代码冻结期间删掉了用户的生产数据库。

## 八、零基础友好：让 AI 替你跑检查（免终端 / 免 SQL）

> **这一节专门解决一个矛盾**：本清单前面要求你跑 SQL / curl / grep，
> 但本套规则的受众是"看不懂代码"的人。你**不需要自己会跑**——让 AI 在你的项目环境里替你跑，你只看它贴回来的结果。

### 做法

把下面这段直接发给你的 AI（替换方括号里的内容），让它执行并把结果翻译成人话给你：

```
我要上线了，请按这份安全清单帮我自查（项目后端是 [Supabase/Postgres，或你的后端]）：

1. 检查数据库权限：列出哪些表没开行级安全（RLS）；已有策略里有没有形同虚设的（qual 是 true、或没引用用户ID）
2. 像攻击者一样试一次：不登录能不能读到任何用户数据
3. 密钥检查：构建产物 / 代码里有没有 service_role、sk_live、AWS 密钥这类不该出现的东西
4. 越权测试：如果有登录系统，模拟用户 B 去读用户 A 的数据，看能不能读到
5. 其他：限流、CORS、错误信息有没有把内部细节泄露给前端

每条给我：你实际执行了什么、看到了什么、结论是什么（安全 / 有问题）、有问题怎么修。
不要编造结果——你实际没跑过的就说没跑。
```

### 你只需要自己点的部分（完全不用终端）

- **越权测试（第三节）**：注册两个账号，用 B 去读 A 的数据——这全程在浏览器里点，不用任何命令。
- **看 AI 的汇报**：AI 跑完 SQL / curl / grep 后，你只要确认它给了"执行了什么 / 看到什么 / 结论"三件套，并且没有用"看起来没问题"这种空话搪塞你。

> 原则不变：**你做判断，AI 干活。** 安全检查也一样——你不必会跑命令，但你必须看结果、做拍板。

## 九、其他后端适配思路（Supabase / Neon / Cloudflare D1）

本清单的 SQL 与命令以 Supabase / Postgres 为例。如果你用的是其它后端，机制不同但**要检查的项完全一样**（RLS 等价物、密钥不出前端、越权测试、限流）。下面是三种常见后端的取舍（核实于 2026-10，会过时，使用前请复核）：

| 方案 | 免费额度 | 最先撞到的墙 |
|---|---|---|
| **Supabase** | 2 个活跃项目、500MB 库、5 万月活 | 一周没流量自动暂停，要手动恢复 |
| **Neon** | 100 个项目、每个 0.5GB | 存储 0.5GB，总量 20GB 封顶；空闲休眠但不暂停 |
| **Cloudflare D1** | 每天 500 万行读 / 10 万行写 | 超限直接报错，不是变慢 |

**国内访问**：Supabase 和 Cloudflare 在国内有时不稳。要直连稳就得看腾讯云开发 CloudBase，但它的免费体验环境是 2026 年 1 月起的一次性兑换码、每月 3000 资源点且功能受限，个人版 ¥19.9/月起。

**所以"免费、省事、国内稳"只能同时满足两个。** 选哪个由你拍板，AI 只给候选清单。
