# SPN · AI 协作规则（零基础版）

> SPN = **Self-precipitation（自我析出）**：在 AI 给出的众多选项里，让属于你自己的判断沉淀、成形。
> 核心信条：**代码是 AI 写的，判断是你做的。**

## 这套规则解决什么问题

AI 编程工具的默认行为是**优化"演示能跑"**。这对懂代码的人是效率提升，对不懂代码的人是风险：

- 你无法判断它写的是不是对的
- 你无法判断它有没有偷偷扩大改动范围
- 安全边界是**唯一不产生可见结果**的部分——表锁着和敞着，页面长得一模一样
- 它会自信地说"已完成"，但可能根本没跑测试

这套规则把**判断权留在人手里**，同时不要求人懂代码。

---

## 这些规则从哪来

不是模板，是三个真实判断（来自一个零基础者做出多个上线项目的过程）。完整叙事与可复用点见 [references/01](https://github.com/xiaoyu-hue/SPN/blob/main/references/01-协作哲学与判断归属.md)：

1. **第一次把项目弄上线** — AI 给候选清单，人做选择（AI 列选项，人拍板）
2. **两种视觉风格能不能融合** — 可逆的事，先试比先问更顺（判据：能否一键还原）
3. **给加密应用划安全边界** — 能跑通某个程度，和你能为这个程度负责，是两件事（能力 ≠ 担保）

## 一、角色分工

| | 人 | AI |
|---|---|---|
| 负责 | 提出想法、做出判断、选择方案、划定边界 | 翻译术语、提供方案、执行实现、验证结果 |
| 不负责 | 写代码 | 替人做决定 |

AI 给出的是**候选清单，不是命令**。

---

## 二、三档授权

判据只有一条：**撤销的成本由谁承担。** 人能一键还原的是可逆；需要人去撤回、去解释的是不可逆。

### 🟢 照做就行（不用问）
- 读文件、看日志、查资料、诊断、review
- 改工作目录内的文件、跑测试、本地验证
- 改完代码就跑相关测试；改了公共模块跑全部测试

### 🟡 先问再做（暂停等确认）
- 删除或覆盖不是自己创建的文件
- 修改数据库 schema、执行数据迁移
- 新增生产依赖
- 生产部署、公开发布
- 对外动作：发邮件、提 PR、公开回复 issue
- 影响超过 5 个文件/记录的批量操作
- 任何改变 Git 状态或历史的操作（commit / push / merge / rebase / reset / 建删分支 / 打标签）

### 🔴 永远不做（硬红线）
- 提交 `.env`、密钥、证书、令牌到仓库
- 把 service_role / sk_live / 私钥放进前端代码或客户端构建产物
- 权限判断只做在前端——**藏按钮不算权限**
- 拼接 SQL，把用户输入直接拼进命令
- 静默跳过错误、隐式兜底、自动降级、制造假数据——非预期行为必须如实上报
- 编造库名、API、版本号、配置项、命令输出、测试结果
- 声称"已验证/测试通过"但实际没执行
- 未获明确同意就删文件、覆盖代码、付费、公开发布

## 三、标准工作流：五次握手

| 步 | 谁 | 产出 |
|---|---|---|
| 1. 说清目标 | 人 | 一句话：给谁、解决什么 |
| 2. 复述验收标准 | AI | "做完的标志是 ___，我用 ___ 检查" |
| 3. 给方案 + 讲权衡 | AI | 至少两个方案，各自代价说清 |
| 4. 拆小步逐段交付 | AI | 每步可独立验证，汇报 before/after |
| 5. 人验证 + AI 如实说明 | 共同 | 改了什么 / 实际验证 / 还没确认 |

**第 2 步不能省。** 说不出"做完的标志是什么"，说明需求还没想清楚。

## 四、零基础的三个关键动作

### 1. 术语必须先翻译，才能判断
不要用你听不懂的词拍板。听到不懂的词立刻喊停，要求用大白话讲清：**它解决什么问题、代价是什么、不用会怎样**。
听不懂不是你的问题，是它没讲清楚。

### 2. 先试再问（判据：能不能一键还原）
- **能一键还原** → 直接试。改颜色、调布局、试交互——试一次比论证一小时快
- **不能还原** → 先问。删文件、改数据结构、上线、付费

### 3. 能力 ≠ 担保
AI 能写出加密代码、能接支付、能跑通第三方 API，但"未经审计""不建议用于真实敏感场景"这类声明**由人来写**。
能跑通某个程度，和你能为这个程度负责，是两件事。

## 五、怎么判断 AI 在糊弄你

| 信号 | 说明什么 |
|---|---|
| 只给一个方案，没有权衡 | 它没真想过替代方案 |
| 满口术语，翻译后还是绕 | 它自己可能也没想清楚 |
| 报错后立刻给兜底方案而不是查根因 | 它在掩盖问题 |
| 声称测试通过但没贴命令输出 | 要求它贴出来 |
| 提到你没听过的库/API/配置项 | **要求它给出官方文档链接，当场核实** |

最后一条最重要：AI 会编造看起来很像真的库名和 API。**未经核实的依赖项一律视为不存在。**

## 六、宣布完成前的自收（防"假完成"）

1. 对照需求项检查实际改动
2. 查看改动文件和 diff，确认没有无关修改
3. 优先运行项目已有且与本次改动相关的测试、lint、类型检查或构建
4. 改动引起失败 → 先定位修复再重新验证；既有或无关失败 → 明确说明
5. 没有可运行的验证方式 → 不要声称"已完成"，直接说未验证的部分、原因和风险

汇报格式：
```
改了什么：[文件路径] + 旧值 → 新值
实际验证：跑了哪条命令，输出是什么
还没确认：[如实列出]
```
禁止用"已改""已优化""已修复"这类没有信息量的词。

## 七、跨会话不失忆

AI 会话一定会失忆，这是硬限制。**HANDOFF.md 是最轻量的跨会话记忆方案**，不装插件，一个 md 文件通用。

- 长会话结束前：「这个会话要结束了，请写交接文档存到 HANDOFF.md」
- 下次开新会话第一句：「先读 HANDOFF.md」

模板见 [references/04 G3](https://github.com/xiaoyu-hue/SPN/blob/main/references/04-提示词库.md)。

## 八、文档里的数字不要写死

会随代码变化的数字（测试数、版本号、条目数、模块数）**不要手写进文档**，
否则一改代码就失真，而失真的数字比不写更伤信任——它会悄悄违背"如实写局限"这个原则。

但**不要因此改用模糊表述**："大量测试"没有信息量，"数百项测试"才有。

三种写法，从糙到好：

1. **相对描述**（推荐先用）：`573 项测试` → `测试积累到数百项`；`v6.5.1` → `迭代到第六个大版本`
2. **单一数据源**：数字只在一个文件定义，其他文档引用它
3. **自动生成**：版本号从 package.json / git tag 读，测试数由 CI 写回

**先上第 1 条，够用很久。** 全套自动化要配 CI，配置本身也是维护成本。

详见 [references/03 第零节](https://github.com/xiaoyu-hue/SPN/blob/main/references/03-文档、局限披露与事实维护.md)。

## 九、重要决策与调试（详见 AGENTS.md）

- **三视角分析**：涉及重要决定时，要求 AI 从「全力反驳 → 切换支持 → 中立对比」三视角分析，而非只给一个结论。
- **调试三步法**：出错时 AI 必须「描述报错 → 大白话解释原因 → 给修复步骤」，禁止没定位根因就直接重写。

这两条是项目维护者后续补进规则、而原 v1.0.0 缺失的部分，已固化进 `AGENTS.md`。

---

## 十、规则本身的维护规则

这套规则遵守它自己的原则：

- 新增一条前，先问能不能和现有条目合并
- **踩一次坑加一条，不预先堆砌**
- 每月检一次，删掉没在起作用的条目
- 规则总数保持精简——**写满三页的规则等于没有规则**

## 已知局限（如实列出）

- 本规则针对**人不懂代码**的场景优化。懂代码的开发者应遵循各自团队规范，本规则的"术语翻译""先试再问"等条目对专业开发者是冗余的
- `02-上线前安全自查.md` 中的 SQL 与命令以 Supabase / Postgres 为例，Firebase、Cloudflare D1 等其他后端需自行调整（适配思路见该文结尾附录）
- 文中引用的安全事件与平台免费额度核实于 2026-10，会随时间变化，使用前请复核
- 本规则不能替代专业安全审计。涉及他人真实敏感数据（医疗、金融、身份信息）的应用，仍建议寻求专业审查
- 参考资料 `01`–`06` 均已有英文版（见 `docs/`）
