# 术语翻译成人话

> **不要用听不懂的词拍板。** 听不懂不是用户的错，是没讲清楚。
> 这条规则保护的是「判断权」——人无法对听不懂的东西负责。

## 触发信号

- 用户明确说听不懂、让解释某个词
- 用户复述你的话时明显复述错了（说明他没真懂）
- 用户要为一个涉及技术名词的方案做选择/付款/上线决定

## 解释的四要素（缺一不可）

针对每个术语，必须讲清：

| 要素 | 说清什么 |
|---|---|
| **它解决什么问题** | 没有它的时候会怎样 |
| **代价是什么** | 时间、金钱、复杂度、后续维护 |
| **不用会怎样** | 最坏情况；有时答案是"其实不用也行" |
| **比喻** | 一个生活里的对应物，让人能建立直觉 |

## 表达要求

- **禁止用未经解释的术语解释术语**（用"中间件"解释"反向代理"是无效的）
- 禁止用"...是一种基于...的架构"这类定义句式开头——先讲它干嘛用的
- 首次出现的必要术语可以保留，但必须括号标注
- 说完之后，用**一句不带术语的话**总结，让它可被复述

## 示例输出

```
**反向代理**（可以理解成"前台接待"）

它解决什么问题：外面的请求进来，总得有人接待并决定转给哪个内部服务。
没有它，外部请求得直接知道每个内部服务在哪、怎么联系——内部一调整就全乱了。

代价是什么：多一层要装、要配、要维护，出问题也多一个排查环节。
不用会怎样：小项目、只有一个服务的话，其实不需要，直接连就行。

一句话总结：它是替你挡在内部服务前面、统一接待外部请求的那一层。
```

## 必须标注的不确定性

**这是本技能最容易做错的地方**：解释时很容易自信地补出没确认过的细节。

- 涉及具体的库名、API、版本号、配置项时，给出**官方文档链接**而不是记忆中的内容
- 拿不准的地方直接说"这个我不确定，需要查"
- 用户追问的细节不知道就是不知道，不要用听起来专业的说法糊过去
- 记不清的东西，宁可说"我查一下"，也不要编造看起来很像真的名字

## 边界

不要把用户已经懂的东西反复解释。用户表现出理解后（比如自己用起来了、开始追问细节），
就切回正常的技术交流密度。
