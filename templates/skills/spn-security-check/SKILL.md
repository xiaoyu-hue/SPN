# 上线前安全自查

> 这份清单存在的理由：**权限错误在演示里完全看不出来。**
> 数据表锁着和敞着，页面长得一模一样——所以必须主动攻击自己，而不是"看起来没问题"。

## 什么时候该用

出现以下任一信号：

- 准备部署上线、分享给别人用、发布到公网
- 项目里有数据库、用户登录、任何"别人的数据"
- 用户问"这样安全吗""会不会被人看到"
- 接入了第三方 API / 支付 / 邮件发送

## 执行前先说一句

先告诉用户你会执行哪些检查、需要他在浏览器里配合做什么（通常是注册两个账号），
**不要默默跑完再说**，也不要因为"看起来没问题"就跳过他看不见的部分。

## 检查清单（按顺序，不许跳）

### 1. 数据库行级安全（最高优先级）

查哪些表没开行级安全（RLS），以及已有策略是不是形同虚设：

```sql
-- 没开 RLS 的表
select tablename from pg_tables where schemaname = 'public' and not rowsecurity;

-- 已有策略，重点看 qual
select tablename, policyname, qual from pg_policies where schemaname = 'public';
```

**判为失败的情况**：`qual` 是 `(true)`；或完全没引用 `auth.uid()`；
或只用了 `auth.role() = 'authenticated'`（那只验证"登录了"，没验证"是不是你自己的数据"）。

正确写法：

```sql
alter table public.documents enable row level security;
create policy "Users read own docs" on public.documents
  for select to authenticated
  using ( (select auth.uid()) = user_id );
```

### 2. 像攻击者一样实打实请求一次

不登录，用公开可拿到的地址和密钥去取数据：

```bash
curl "https://PROJECT.supabase.co/rest/v1/profiles?select=*" -H "apikey: ANON_KEY"
```

**不登录就能拿回数据 = 正在泄露。** 返回空数组或权限错误才是对的。

### 3. 越权测试（这一步必须让用户亲手做）

1. 注册**两个**账号 A 和 B
2. 用 A 创建一条数据
3. 用 B 去读它——改请求里的 id、改 URL 参数都行
4. **B 能读到 = 权限没配对**

> 这全程在浏览器里点，不需要用户会用命令行。这是整套检查里**唯一必须他亲自动手**的一项。

### 4. 密钥与构建产物

```bash
grep -r "service_role\|sk_live\|AKIA[0-9A-Z]\{16\}" dist/ build/ .next/ 2>/dev/null
```

任何命中都是严重问题。anon key 出现在前端是正常的（它本来就是公开的），
**service_role 出现则是致命的**。另外：`.env` 必须在 `.gitignore` 里，
且要在**第一次 commit 之前**就加进去；密钥一旦进了 git 历史，删掉那一行也没用，必须轮换。

### 5. 其他必查项

| 项 | 怎么判 |
|---|---|
| 服务端校验 | 所有输入在服务端校验；发现拼接 SQL 立刻停下报告 |
| 限流 | 注册、登录、发邮件、AI 调用这类"花钱的接口"必须限流，否则一个脚本能烧掉额度 |
| CORS | 锁到自己的域名，不留 `*` |
| 依赖漏洞 | 跑 `npm audit` / `pip-audit`，AI 生成的项目几乎从不做这件事 |
| 错误信息 | 不把堆栈、SQL、内部路径返回给前端 |
| 备份 | 免费档通常不含自动备份——要验证过能恢复才算数 |

## 输出格式（每条都要有）

```
### [通过 / 有问题] 检查项名称
执行了什么：<具体命令或操作>
看到了什么：<实际返回，不能只写"没问题">
结论：<安全 / 有问题>
有问题怎么修：<可执行的修复步骤>
```

**禁止**：
- 没实际执行就写"已检查""看起来没问题"
- 把"我没找到问题"说成"没有问题"——这两句意思不同，前者才是实话
- 替用户写安全声明（"未经专业安全审计"这类边界声明由人自己写，AI 不代笔）

## 边界声明

这不是专业安全审计，也替代不了。**本清单提供的检查项的具体数据来源与核查日期见 SPN 仓库的 `FACTS.md`。**
识别出**排查范围之外**的风险（比如涉及医疗、金融、身份信息）时，必须明确建议寻求专业审查。
