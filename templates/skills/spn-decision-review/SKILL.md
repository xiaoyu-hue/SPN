# 决策审查（动手之前先反问）

> 与「做完之后写记录」的 CHANGELOG / ADR 互补：**那份记的是已经发生的，这份是阻止你后悔的。**
> 适用于任何项目，不限语言与框架。

## 触发条件（任一成立就必须走这套流程）

| 类别 | 例子 |
|---|---|
| 不可逆操作 | 删除/覆盖文件、删分支、强制推送、改写 git 历史、清空数据 |
| 花钱的操作 | 购买服务、付费 API、升级订阅、云资源、第三方审计 |
| 对外发布 | 发布 Release、公开发文、部署线上、公开仓库 |
| 影响走向 | 架构变更、技术选型、版本号策略、下线既有功能、数据迁移 |

**出现以上任一情况，先答完清单再动手，等拍板人确认。**

## 步骤一：决策三问（缺一不可）

### 1. 坏处 / 代价是什么？
- 有什么缺点、成本、风险？
- 对现有功能、数据、性能、维护成本分别有什么影响？
- **不得轻描淡写或只讲好处**；被追问时必须补齐。

### 2. 不做的后果是什么？
- 不做或推迟做，会失去什么？
- 损失是永久的还是可逆的？
- **如果"不做也没损失"，说明这个方案可能根本不必要。**

### 3. 什么情况下会后悔？
- 哪个前提条件不成立时，这个决定就是错的？
- 多久之后还能反悔？反悔成本多大？
- 有没有"先小规模试点，再决定要不要全做"的空间？

## 步骤二：至少给一个替代方案

**只给单一方案等同于替人做决定。** 必须说清为什么不用替代方案，
并且要能区分：排斥的理由是**真实约束**，还是**习惯**。

## 步骤三：把代价说完，再问要不要继续

最容易漏的一步：**用户明确表态之后也要先把缺陷说清**。
用户说"我就要这个方案"，你回答"好的可以"，却不指出代价——这同样是在替他做决定。

正确顺序：**先说清代价和风险 → 再问他是否仍然要做 → 最后执行。**

## 步骤四：填拍板记录（随 PR 或提交一起留存）

```markdown
## 决策记录（DECISION LOG）

- **日期**：YYYY-MM-DD
- **决策人**：拍板人 / 建议方（AI 或他人）
- **要做什么**：（一句话）
- **触发类别**：□不可逆 □花钱 □对外发布 □影响走向

### 决策三问
1. 坏处/代价：
2. 不做的后果：
3. 后悔条件（何时反悔、成本）：

### 替代方案
- 方案 B：（描述）
- 为什么不用 B：

### 安全/隐私影响
- （有则说明，无则写「无」）

### 拍板结论
- □ 做（已确认）  □ 不做  □ 先试点/推迟
- 确认时间：YYYY-MM-DD
```

## 五层追问（三问不够时用）

1. **目标与范围** — 到底要解决什么问题？最小范围是什么？有没有被顺带改掉但无关的东西？
2. **不可逆性** — 能不能撤销？几步？失败的最坏情况是什么？能不能先做可回滚版本？
3. **替代方案** — 有没有更简单/更便宜/更快的做法？排斥理由是真实约束还是习惯？
4. **时间维度** — 现在做和一个月后做差别大吗？有什么正在变化的因素？多久后复审？
5. **安全与隐私** — 涉及数据/密码/密钥吗？文档声明的能力，代码里真有对应实现吗？

> 一句话：**小事直接做，大事先三问，问完拍板写下来。**
