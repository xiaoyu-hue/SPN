# 文档与版本同步

> 核心原则：**版本号问版本元数据，数字问测试输出，描述问代码。**
> 文档不能超出实现——写得比实际好的文档，比没有文档更伤信任。

## 什么时候该用

- 发版前（bump 版本 + tag + Release）
- 功能新增 / 修改 / 移除之后
- 依赖变化、CI / 安全门禁变化之后
- 用户抱怨"文档跟实际对不上"

## 唯一真源原则

| 内容 | 唯一真源 | 文档该怎么处理 |
|---|---|---|
| 版本号 | 版本元数据（`package.json` / `pyproject.toml` / git tag） | 从它派生，不手写 |
| 测试数 / 文件数 | 实际测试命令输出 | 不抄旧数，**重新跑一遍** |
| 功能 / 架构描述 | 代码实现 | 不超过实现 |
| 会变平台额度 / 价格 / 调研数据 | 外部来源 + 核查日期 | 单独登记并定期复核，不要散落在文档里 |

## 同步清单（逐项勾选）

### A. 版本号

- [ ] 版本元数据文件已 bump
- [ ] 锁文件（如 `package-lock.json` / `poetry.lock`）已同步
- [ ] `CHANGELOG.md`：「未发布」条目已转为正式版本条目
- [ ] `README.md`：版本声明 / 徽章
- [ ] 需求 / 设计文档：版本头、状态行、版本历史表
- [ ] Release + tag 与版本元数据一致

### B. 数字与事实

- [ ] 测试数已按**本次实际输出**更新（不是沿用上一版写的数）
- [ ] 依赖清单变化已反映到致谢 / 说明表
- [ ] 漏洞扫描数字（如 `npm audit`）已刷新
- [ ] 功能 / 架构描述与代码实现一致
- [ ] **多语文档已同步**（以基准语言版为权威）

### C. 数字不要写死

会随迭代变化的数字不要手写进文档，否则一改代码就失真。
处理方式按推荐顺序：

1. **相对描述**："测试积累到数百项" 而不是具体数字
2. **单一数据源**：数字只在一个地方定义，其他地方引用
3. **自动生成**：版本号从元数据读，测试数由 CI 写回

先做第 1 条就够用很久。全套自动化要配 CI，配置本身也是维护成本。

## 版本号该怎么动（SemVer）

| 变化类型 | 动作 | 例子 |
|---|---|---|
| 新增用户可见功能 | minor | X.Y.0 → X.(Y+1).0 |
| 修 bug / 安全修复 | patch | X.Y.Z → X.Y.(Z+1) |
| 仅文档 / CI / 工程变更 | patch 或不动 | X.Y.Z → X.Y.(Z+1) |
| 破坏性变更 | major | X.0.0 → (X+1).0.0 |

> 用户能感知的新东西 → minor；修了错 → patch；只是整理 → patch 或不 bump。
> 拿不准就先过一遍决策三问。

## 发布前必须验证（这几条别凭记忆）

```bash
# 1. 旧版本号残留检查：结果应为空，或确认命中仅为历史记录
grep -rn "旧版本号" --include="*.md" --include="*.json" .

# 2. 跑全量测试，核对输出数字与 README 声明是否一致
#    不一致必须改 README，不许改数字假装一致
```

- [ ] 版本元数据 = 锁文件 = CHANGELOG 最新条目 = 文档版本头 = tag
- [ ] 「未发布」条目已转正式，内容覆盖本次全部用户可见变更
- [ ] 多语文档对查完毕

## 边界

**不要为了让文档显得漂亮而夸大能力。** 文档声称有、代码里没有的功能，
比文档缺失更危险——它会让人基于错误前提做决定。
